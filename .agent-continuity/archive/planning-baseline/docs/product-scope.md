# Product Scope

## Prototype goal

This project is a **technical and product interaction prototype**, not a production CRM replacement.

The prototype asks:

> Can an agent transform CRM state into the right working interface and action path without hiding the underlying system of record?

The core value is not an AI chat box. The core value is the loop between **intent, tool use, interpretation, structured workspace rendering, human control, and persistent CRM state**.

## Product model

### Traditional CRM

Users navigate records and views, inspect data, interpret business state, decide what matters, and trigger actions manually.

### Agent-native CRM

The system interprets the current business state and user intent, assembles the required context through tools, and presents a task-oriented workspace.

```text
System of Record
  → Agent interpretation
  → Situation / decision
  → Adaptive workspace
  → Human action
  → Tool execution
  → Updated System of Record
```

The user can always move back down toward the underlying data.

## Primary surfaces

### 1. Today

Purpose: answer **"What needs my attention?"** while preserving global awareness.

The page should contain:

- deterministic CRM totals such as active deals and pipeline value;
- a small set of agent-derived situations;
- a compact agent activity summary;
- a clear route to Explore.

Global facts must not be generated by the LLM. They should come directly from the database/tool layer.

### 2. Workspace

Purpose: provide the interface best suited to the current task.

The workspace is transient and task-oriented. The shell stays stable while the inner workspace changes.

Initial workspace types:

#### Focus

Use when the user asks what deserves attention or wants a prioritized subset.

Typical contents:

- short summary;
- situation cards;
- key evidence;
- suggested next step.

#### Investigation

Use when the user asks what happened with a specific deal/account or why something is risky/important.

Typical contents:

- situation summary;
- timeline;
- evidence;
- recommendation;
- optional action.

#### Comparison

Use when the user asks to compare a small set of records.

Typical contents:

- comparison table;
- relevant differences;
- optional interpretation/recommendation.

### 3. Explore

Purpose: act as the conventional CRM fallback and inspection/control layer.

The MVP only needs lightweight access to:

- customers;
- deals;
- activities;
- tasks;
- a simple pipeline/table view.

Explore exists so users can verify that the underlying data is real, understand the overall system state, and manually inspect records when needed.

It is not intended to become a feature-complete CRM.

## Agent responsibilities

The agent may:

- infer intent;
- choose which approved tools are needed;
- decide which supported workspace type best fits the task;
- interpret returned CRM data;
- rank or summarize situations;
- propose actions;
- produce validated structured workspace output.

The agent may **not**:

- invent CRM facts;
- generate arbitrary executable UI code;
- bypass tool permissions;
- execute consequential mutations without required approval;
- hide the existence of the underlying data/control path.

## Data responsibilities

The database/tool layer owns facts.

Examples of facts:

- deal value;
- stage;
- customer name;
- activity timestamps;
- task status;
- pipeline totals.

The LLM owns interpretation of those facts.

Examples of interpretation:

- "deal momentum appears to be slowing";
- "this account deserves attention";
- "these two deals are behaving differently";
- "a follow-up task is the most useful next action".

**Rule:** facts deterministic; interpretation generative.

## Initial tool surface

Keep the tool set deliberately small.

### Read tools

- `get_crm_summary`
- `list_deals`
- `get_deal`
- `get_account_context`
- `get_recent_activities`

Context tools are allowed to aggregate related source data, but should not perform LLM reasoning internally.

### Mutation tool

Choose only one meaningful mutation for the first demo:

- `create_task`, or
- `update_deal_stage`.

The mutation must be proposed first, approved by the user, then executed.

## Reference demo scenario

Seed a small, believable CRM dataset where at least two deals contain meaningful signals.

Example:

### ACME

- high-value proposal;
- no meaningful response for several days;
- unresolved security questions;
- recent proposal activity.

### Nova

- recent engagement;
- strong buying signals;
- clear next-step opportunity.

Demo flow:

1. User asks: **"What should I focus on today?"**
2. Agent uses tools to inspect CRM state.
3. Focus workspace highlights ACME and Nova with evidence.
4. User asks: **"Why ACME?"**
5. Agent retrieves account context.
6. Investigation workspace renders timeline, evidence, and recommendation.
7. User asks to create a follow-up task.
8. Agent proposes the mutation.
9. User approves.
10. Tool executes and Explore shows the updated task.

## Scope guardrails

If a proposed feature does not strengthen the reference demo or validate the research question, defer it.

In particular, do not expand into:

- full CRM modules;
- email/calendar integration in Phase 1;
- large tool catalogs;
- arbitrary generative UI;
- persistent agent memory;
- multi-agent systems;
- workflow builders;
- autonomous outbound communication;
- complex permissions beyond what the demo needs.

## Success criteria

The MVP is successful when:

1. a real LLM interprets natural-language CRM requests;
2. the agent selects and executes appropriate real tools against seeded CRM data;
3. the agent returns schema-valid workspace output;
4. different intents can produce different supported workspace forms;
5. the user can inspect the evidence and underlying CRM records;
6. at least one approved mutation updates persistent CRM state;
7. the complete flow is understandable without explaining hidden demo tricks.
